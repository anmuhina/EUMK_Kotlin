Раздел 4. Тестирование, отладка и публикация приложений

4.1. Роль тестирования в разработке мобильных приложений

Тестирование — неотъемлемая часть профессиональной разработки. Оно позволяет обнаруживать дефекты на ранних этапах, защищает от регрессий при изменении кода и документирует ожидаемое поведение. В Android принято разделять тесты по уровню (пирамида тестирования): модульные (unit) — большинство, быстрые и дешёвые; интеграционные — проверяют взаимодействие компонентов; UI-тесты (instrumented) — проверяют интерфейс на устройстве/эмуляторе, самые медленные и дорогие. Хорошая стратегия — покрывать модульными тестами бизнес-логику (ViewModel, Repository) и использовать UI-тесты для ключевых сценариев.

4.2. Модульные (unit) тесты

Модульные тесты проверяют отдельные функции и классы в изоляции, без Android-устройства, на JVM. Они выполняются быстро (секунды) и запускаются в IDE и на CI. Фреймворк — JUnit (аннотации @Test, @Before, @After, @BeforeClass; утверждения assertEquals, assertTrue, assertThrows).

class Calculator {
    fun add(a: Int, b: Int) = a + b
}

class CalculatorTest {
    @Test
    fun testAddition() {
        val result = Calculator().add(2, 3)
        assertEquals(5, result)
    }
}

Тестирование корутин. Для suspend-функций используется runTest из kotlinx-coroutines-test, который управляет виртуальным временем и позволяет тестировать delay без реального ожидания. Для Flow применяется turbine (библиотека) или ручной сбор. Тестирование ViewModel с StateFlow — через runTest и проверку эмитированных значений.

@Test
fun `state emits Success on load`() = runTest {
    val vm = UserViewModel(FakeRepository())
    vm.load("1")
    advanceUntilIdle()
    assertTrue(vm.state.value is UiState.Success)
}

Тестовые дублёры. Внешние зависимости (сеть, БД) заменяются фейками (простые реализации интерфейсов) или моками (Mockito/MockK). Это позволяет тестировать логику без реальных сетевых вызовов и делает тесты детерминированными.

4.3. UI-тесты (instrumented)

UI-тесты запускаются на реальном устройстве или эмуляторе и проверяют взаимодействие пользователя с интерфейсом: нажатия, ввод текста, отображение элементов. В Compose используется библиотека Compose Testing (createComposeRule, onNodeWithText, performClick, assertIsDisplayed), в классических View — Espresso. UI-тесты медленнее и требовательнее к окружению, поэтому их количество ограничивают ключевыми сценариями.

@get:Rule
val composeRule = createComposeRule()

@Test
fun buttonClick_showsText() {
    composeRule.setContent { SimpleInputScreen() }
    composeRule.onNodeWithText("Введите текст").performTextInput("Привет")
    composeRule.onNodeWithText("Показать").performClick()
    composeRule.onNodeWithText("Привет").assertIsDisplayed()
}

4.4. Отладка в Android Studio

Logcat. Основной инструмент диагностики. Логи пишутся через Log.d/i/w/e(tag, message) и фильтруются по тегу, уровню, процессу. Logcat показывает стектрейсы исключений, системные сообщения и логи сторонних библиотек. В продакшене логирование ограничивают и не выводят персональные данные.

Отладчик (Debugger). Позволяет ставить точки останова (breakpoints), выполнять код по шагам (step over/into/out), просматривать значения переменных, вычислять выражения (Evaluate Expression) и анализировать стек вызовов. Условные точки останова останавливают выполнение только при заданном условии.

Layout Inspector. Показывает дерево UI в реальном времени, свойства элементов и их размеры — полезно для диагностики проблем верстки.

Профилировщики (Profiler). CPU Profiler выявляет «тяжелые» методы, Memory Profiler — утечки памяти, Network Profiler — сетевые запросы и их размер, Energy Profiler — энергопотребление. Профилирование помогает оптимизировать производительность и не допускать ANR (Application Not Responding).

Типичные проблемы. NullPointerException (нарушение null-безопасности через !!), утечки памяти (ссылки на Activity из статических полей, неотменённые корутины), ANR (долгие операции в главном потоке), NetworkOnMainThreadException (сетевые вызовы без Dispatchers.IO).

4.5. Подготовка приложения к публикации

Сборка APK/AAB. Android Studio собирает APK (устанавливаемый файл) и AAB (Android App Bundle) — формат, обязательный для публикации в Google Play с 2021 года. AAB содержит все ресурсы и код, а Google Play генерирует оптимизированные APK под каждое устройство (split APK), что уменьшает размер загрузки.

Подпись. Приложение должно быть подписано криптографическим ключом. Для отладки используется debug-ключ, для публикации — release-ключ (keystore). Ключ и пароли хранятся в защищённом месте и не попадают в репозиторий. Настройка подписи выполняется в build.gradle.kts через signingConfigs.

android {
    signingConfigs {
        create("release") {
            storeFile = file("release.keystore")
            storePassword = System.getenv("STORE_PASSWORD")
            keyAlias = "release"
            keyPassword = System.getenv("KEY_PASSWORD")
        }
    }
    buildTypes {
        release {
            isMinifyEnabled = true
            isShrinkResources = true
            signingConfig = signingConfigs.getByName("release")
        }
    }
}

Minify и shrinkResources. R8/ProGuard удаляет неиспользуемый код и обфусцирует имена, уменьшая размер APK и затрудняя реверс-инжиниринг. shrinkResources удаляет неиспользуемые ресурсы. При обфускации нужно сохранять правила (proguard-rules.pro) для библиотек, использующих рефлексию.

Версионирование. В build.gradle.kts задаются versionCode (целое число, увеличивается с каждой публикацией) и versionName (строка для пользователей, например «1.0.0»). Google Play требует, чтобы versionCode монотонно возрастал.

4.6. Публикация в Google Play

Процесс публикации:

  1. Создание аккаунта разработчика (единоразовый платёж) и принятие соглашений.
  2. Создание приложения в Play Console: название, описание, категория, контент-рейтинг, политика конфиденциальности.
  3. Подготовка ресурсов: иконка, скриншоты, feature graphic, промо-тексты.
  4. Загрузка AAB в выбранный трек: internal testing → closed testing → open testing → production. Поэтапное тестирование снижает риски.
  5. Заполнение карточки: описание, скриншоты, возрастной рейтинг, данные о сборе данных (Data Safety).
  6. Отправка на проверку (review) — модерация Google занимает от нескольких часов до нескольких дней.
  7. Публикация и мониторинг: анализ отзывов, крашей (Android Vitals), обновления.

Требования Google Play: целевой API level должен соответствовать актуальным требованиям; обязательна политика конфиденциальности при сборе данных; запрещены опасные разрешения без обоснования; приложение не должно нарушать политики (спам, вредоносное ПО, нарушения прав).

4.7. Основы CI/CD для мобильных проектов

CI (Continuous Integration) — автоматическая сборка и тестирование при каждом коммите. CD (Continuous Delivery/Deployment) — автоматическая доставка сборок в треки Google Play. Популярные инструменты: GitHub Actions, GitLab CI, Bitrise, Jenkins. Типичный пайплайн: checkout → сборка → unit-тесты → lint → сборка release AAB → (опционально) публикация в internal testing. Секреты (ключи подписи, токены) хранятся в защищённых переменных CI, а не в репозитории.

# Пример фрагмента GitHub Actions
jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-java@v4
        with: { distribution: 'temurin', java-version: '17' }
      - run: ./gradlew test
      - run: ./gradlew bundleRelease

4.8. Управление версиями и совместная работа

Git — распределённая система контроля версий. Базовые команды: git init, git add, git commit, git push, git pull, git branch, git merge, git rebase. В Android-проектах используется .gitignore для исключения build/, .gradle/, local.properties, *.keystore. Рекомендуемые практики: осмысленные сообщения коммитов, ветвление (feature branches), код-ревью через pull/merge requests, теги для релизов.

1. Чем unit-тест отличается от UI-теста?

Показать правильный ответ
Ответ: Unit-тест проверяет код на JVM без устройства, UI-тест — интерфейс на устройстве/эмуляторе.

2. Что делает аннотация @Test?

Показать правильный ответ
Ответ: Помечает метод как тестовый.

3. Что делает @Before?

Показать правильный ответ
Ответ: Выполняется перед каждым тестом (подготовка).

4. Для чего нужен Logcat?

Показать правильный ответ
Ответ: Для просмотра логов и ошибок приложения.

5. Чем APK отличается от AAB?

Показать правильный ответ
Ответ: APK — готовый файл для установки, AAB — формат для публикации в Google Play (Play сам собирает APK).

6. Зачем нужна подпись приложения?

Показать правильный ответ
Ответ: Подтверждает авторство и целостность; без неё нельзя опубликовать и обновлять приложение.

7. Что такое CI/CD?

Показать правильный ответ
Ответ: Автоматическая сборка, тестирование и доставка приложения.
